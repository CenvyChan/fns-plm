# 项目管理数据模型与设计依据

> 本文记录本系统项目管理与事件绩效功能的设计约束；它不是 ISO/PMI 认证声明，也不替企业设定未经批准的 KPI 目标值或权重。

## 设计约束

1. **生命周期可配置**：项目从立项到结项；租户可按项目类型套用阶段模板。阶段、计划/实际日期、进度、责任人和状态均可追溯。
2. **按交付物分解范围**：项目工作采用可编号的层级工作包与可执行任务；任务应有单一责任人、计划日期、依赖关系及验收标准。项目、阶段、里程碑、任务与事件相互引用，不能只以自由文本描述进展。
3. **进度可度量**：任务记录计划/实际开始与结束、负责人、估算/实际工时、进度、前置依赖；里程碑与项目阶段进行汇总，甘特视图读取同一份数据。
4. **事件留痕**：会议、决策、风险、问题、变更、交付等事件保存创建人、创建时间、责任人、计划日期、处理状态、关联阶段/里程碑/任务和附件。
5. **事件级绩效双阶段评审**：项目事件可生成绩效评审，先由执行人自评、再由主管评审；每条评分绑定 KPI 规则的历史快照（名称、公式、方向、目标、权重、版本），避免规则修改后改变既有评审结果。总分按权重归一化计算：`Σ(分项得分 × 分项权重) / Σ(纳入评审的分项权重)`；规则达到目标的得分为 100，按方向计算并限幅，主管得分在最终分中优先于自评分。每步保存评审人、意见与时间戳。
6. **加权汇总与固定规则**：KPI 规则以草稿/生效状态及版本管理。生效集的权重应按组织要求合计 100%；新规则先草稿，明确“待启用”并说明校验条件。事件得分可按项目中设定的事件权重汇总为项目绩效点。
7. **附件与交付包**：附件在受保护文件存储中保存原文件名、哈希、大小、上传人和时间；ZIP 交付包只包括所选项目的 JSON/Excel、报告及附件，不携带数据库、密钥、环境变量、其他项目或账套数据。当前项目级附件归档名为 `{项目编号}_NA_NA_{创建人}_{UTC时间戳}_{附件ID}_{原文件名}`；事件号/任务号暂无直接关联时使用 `NA`，附件 ID 用于消除同名/同时上传冲突。manifest 保留原始名称、归档名、关联记录、创建人、时间、SHA-256，并标明附件二进制是否进入归档。
8. **范围与集成隔离**：所有项目数据与 Flowable、K3Cloud、钉钉配置都按内部 `(tenantId, organizationId, accountId)` 三元组读写；外部系统的租户/组织/账套标识和用户映射单独记录。缺少凭据或映射时明确显示未配置/未连通，不以模拟状态冒充生产连接。

## 对应数据实体

- `Project`：编号、名称、类型、部门、负责人/发起人、阶段、计划与实际日期、状态、优先级、范围/目标/成功标准、进度。
- `ProjectPhase` / `ProjectMilestone`：阶段顺序、计划/实际日期、责任人、验收状态。
- `Task`：WBS 编号、阶段/里程碑关联、负责人、依赖、日期、工时、进度及验收标准。
- `ProjectEvent`：事件类型、编号、关联对象、负责人、日期、状态、创建信息与附件。
- `ProjectEventReview`：评审状态、自评/主管评分与意见、规则快照、分项权重、加权结果及审计时间。
- `ProjectReport`：报告周期、进展、完成项、风险/阻塞、决策需求、下一步与作者。
- `ProjectTemplate`：项目类型、阶段、里程碑与任务的可复用蓝图。
- `ProjectAttachment`：文件元数据和账套隔离关联；二进制内容独立受控存储。

## 公开来源（访问日期：2026-10-15）

- ISO，《Improving project management》：ISO 21502 覆盖项目生命周期中的规划与控制，包括风险、问题、变更控制、收益与信息管理。<https://www.iso.org/news/ref2645.html>
- PMI，《Work Breakdown Structure: Define the Work Before You Build It》（2026-08-18）：工作分解结构是面向交付物的层级分解；工作包应有唯一标识和单一责任方，配套范围、里程碑、负责人及验收标准，并遵守 100% 原则。<https://www.pmi.org/blog/work-breakdown-structure>
- PMI，《Scheduling 101—the basic of best practices》（2009-10-13）：可执行计划由 WBS、工作包、活动逻辑、资源与时间共同构成；进度活动应可度量。<https://www.pmi.org/learning/library/schedule-101-basic-best-practices-6701>
- PMI，《Anatomy of an effective status report》（2014-06）：状态汇报宜简洁、结构清晰；报告应让干系人看清总体状态、团队分工、里程碑与实际进展。<https://www.pmi.org/learning/library/anatomy-highly-effective-status-report-2198>
